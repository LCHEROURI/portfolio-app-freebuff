# Review, main (uncommitted model-label work), 2026-08-04

**Reviewed by**: deepseek flash, inline fallback (author on deepseek flash, so this review shares the author model's blind spots; the contrasting model subagent was unavailable in this environment)
**Scope**: 8 files, uncommitted working tree changes on main
**Verdict**: Approve with nits

## Summary

The change adds a friendly display label for OpenRouter model ids wherever AI-generated content shows its source model: a `MODEL_LABELS` map plus a `modelLabel()` helper in lib/labels.ts, a reusable `ModelBadge` component in components/ui/Badge.tsx that shows the friendly label with the raw id as a hover tooltip, and swaps the three raw-id badges (Command Center briefing, Reports executive summary, Model Comparison winner recommendation) over to it. The design is clean and follows the existing label-map pattern in the same file. Unknown model ids fall back to the raw id, and null or undefined render no badge at all. Unit tests cover the map, the fallback, the tooltip, and the null case, and the page tests were updated to expect the friendly labels.

## Major

None.

## Minor

### 🟡 Emailed report headings still show the raw model id, `lib/openrouter.ts:349` and `lib/openrouter.ts:360`
**Problem**: `withExecutiveSummary` and `withTopThreeNarration` render `(deepseek/deepseek-chat)` inside the email section headings, while every in-app badge now shows the friendly label. The mapping exists in lib/labels.ts but is not applied to the email body.
**Why it matters**: A user reading the emailed daily report sees the raw id while the same content in the app shows the friendly label. Small, but it is the one place the model id still leaks through unfriendly.
**Suggested fix**: Apply `modelLabel()` to the model argument in both heading builders, or keep the raw id deliberately and document that choice. Not blocking.

## Nits

- ⚪ `lib/labels.ts:42`, `MODEL_LABELS` is a plain `Record<string, string>`; an `as const` or `satisfies` would keep the label strings type-checked against the map, but the current form matches the neighboring `QUEUE_RULE_LABELS` and `PROVIDER_LABELS`, so consistency wins.
- ⚪ `components/ui/ModelBadge.test.tsx:10`, the test finds the title via `badge.closest('span')`; since the badge renders a single span, `toHaveAttribute` on the element returned by `getByText` would be equally correct and slightly more direct.

## Strengths

- The hover-tooltip keeps the exact raw model id available, so the friendly label never hides which model actually wrote the content — a genuinely good tradeoff for the A/B testing use case this app exists to serve.
- The fallback behavior is exactly right: unknown ids show the raw id, empty or null show nothing, and the page tests were updated in the same change so the suite stayed green.

## Test coverage

Covered well. `lib/labels.test.ts` verifies the map, self-consistency of every entry, the raw-id fallback, and the null/undefined case. `components/ui/ModelBadge.test.tsx` verifies the label, the tooltip, the fallback, and the empty render. The three page suites assert the friendly labels in the rendered badges. The only untested surface is the email headings noted in the Minor.
