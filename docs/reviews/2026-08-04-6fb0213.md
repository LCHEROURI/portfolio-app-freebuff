## Major

### 🟠 Drill down click during an in flight narration leaves chip scope and content mismatched, `app/command-center/page.tsx:141`
**Problem**: `explainTopThree` returns early when `narrating` is true. `briefProject` runs `setScopeProjectId(projectId)` and `setNarration(null)` and then calls `explainTopThree(projectId)`, but if a previous narration call is still in flight, that call is silently dropped. The old in flight call then resolves and calls `setNarration` with the paragraph for the old scope.
**Why it matters**: The chip for the new project shows pressed while the paragraph shown describes the old project's actions. This is reachable in normal use: click AI Explain, then immediately click a project chip before the request resolves. The user sees a briefing that does not match the highlighted project.
**Suggested fix**: In `briefProject` (and the All chip handler), bail out only when the new call is already in flight for the same target, or track a request id and let the newest request win: when a call starts, record its scope; when it resolves, ignore the result if a newer scope has been selected since. The existing test "clears the previous scope's paragraph while the scoped briefing loads" covers the stale paragraph case but not a dropped click; add a test where the chip is clicked while `narrating` is true.

## Minor

### 🟡 Cron narration sends actions without project identity, `app/api/cron/reports/route.ts:104`
**Problem**: `topThreeActions` maps only priority, title, and description, dropping the `projectId` and `projectName` that the Command Center sends. The narration prompt and the `known` set then never see a project id, so `projectIds` is always empty in the emailed narration.
**Why it matters**: The emailed briefing cannot cite project names even though the dashboard briefing can, so the morning email and the dashboard diverge in how specific they are. It is consistent with the current design (the email has no cite back links) but the drop is undocumented in the mapping itself.
**Suggested fix**: Pass `projectId` and `projectName` through like the Command Center does, and let the email template decide whether to render links. At minimum add a one line comment explaining the drop is deliberate.

### 🟡 Greedy JSON extraction in `parseJsonObject` can swallow trailing prose, `lib/openrouter.ts:215`
**Problem**: The regex `/\{[\s\S]*\}/` matches from the first brace to the last brace in the whole reply. If the model emits the JSON object followed by a closing remark that contains a brace, the extracted text is not valid JSON and the whole narration is discarded.
**Why it matters**: The failure mode is graceful (fallback to rule based text) but a common real world reply pattern (JSON then a short tail) would silently lose the narration. The current tests only cover fences and bare objects.
**Suggested fix**: Try a first `JSON.parse` directly, then strip code fences, then fall back to the brace range extraction. Keep the graceful null on failure.

### 🟡 `narrateTopThree` maxTokens of 220 can truncate the JSON, `lib/openrouter.ts:317`
**Problem**: The reply must be a full JSON object with a paragraph of two to three sentences plus a project id array. At 220 tokens a long paragraph plus the closing brace can be cut off, which makes the JSON unparsable and drops the narration entirely.
**Why it matters**: Graceful but wasteful; the user sees no narration even though the model produced most of it. A slightly higher budget or a JSON only reply with a smaller paragraph target would be more reliable.
**Suggested fix**: Raise the budget modestly (for example 300 tokens) or trim the paragraph target in the prompt.
